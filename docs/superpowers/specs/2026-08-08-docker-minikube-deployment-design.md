# Docker Compose & Minikube Deployment — Design

## Context

The [gRPC inference server design](2026-08-08-grpc-inference-server-design.md) splits today's single-process `repl.py` into a native macOS inference server (`inference_server.py`, Metal-accelerated, owns the model) and a client that keeps the conversation logic (ChatML formatting, `context_tokens`, truncation, interrupt handling) and calls out over gRPC. That spec explicitly deferred containerized deployment of the client side to a future spec — this is that spec.

**Assumption:** the gRPC client/server split, the `inference.proto` contract, `config.py`, and the certs generated by `just setup` are being implemented separately per that spec. This spec does not build or modify any of that — it assumes `repl.py` is (or will be) the gRPC client described there, and builds the deployment layer on top of it.

## Goal

Package the conversation-logic side as a container image, and provide both a Docker Compose file and minikube manifests to run it — reachable over WebSocket from a browser or any WebSocket client — while it calls the inference server running natively on the host machine (never containerized; stays on bare macOS for Metal).

## Out of scope

- Building `inference_server.py`, `inference.proto`, `config.py`, or converting `repl.py` to a gRPC client — assumed to exist per the referenced spec.
- Containerizing or deploying the inference server itself — it stays native on macOS, always.
- Auth, multi-user sessions, session persistence, horizontal scaling, Ingress/TLS termination for the WebSocket itself.
- Solving the TLS hostname mismatch between the inference server's `CN=localhost` cert and the `host.docker.internal` / `host.minikube.internal` names used to reach it from a container. Certs are assumed to already exist (produced by the other spec's `just setup`) and are mounted as-is; making the gRPC channel accept them when dialed via a Docker/minikube host alias is called out below as a known follow-up, not solved here.
- Any change to sampling, context truncation, or the ChatML format.

## Architecture

Today's `repl.py` is a terminal loop: `while True: input()`, printing to stdout. This spec replaces that loop with a hosted WebSocket service — there is no dual terminal/network interface; the terminal loop is removed outright.

- **`repl.py` becomes a FastAPI app.** A `/ws/chat` WebSocket endpoint owns the per-turn logic that today lives in `run_turn`: format the ChatML turn, tokenize locally, truncate context, call the inference server's gRPC `Generate`, stream tokens back. One WebSocket connection = one conversation; `context_tokens` lives in memory for that connection and is discarded on disconnect. No persistence, no auth, no multi-tenancy — this is a direct re-fronting of today's single-user REPL, not a new product.
- **`inference_server.py` is untouched and never containerized.** It keeps running natively via `just serve`, outside Docker and outside minikube, exactly as the other spec describes.
- The container still needs a local `vocab_only=True` `Llama` instance for tokenize/detokenize (per the other spec's design), so the model `.gguf` file must be present inside the container image or mounted into it — in cheap vocab-only mode, no GPU/Metal needed, so this works fine in a plain Linux container.
- Debug detail (top-5 candidate probabilities, prompt-token dumps) that today prints to the terminal moves to server-side `logging` — it is not part of the WebSocket wire format. Clients only see the token stream.

### WebSocket protocol

Client → server: one text frame per user turn (plain text message body).

Server → client, one JSON frame per event:

```json
{"type": "token", "text": "..."}
{"type": "done", "elapsed_s": 1.23, "tokens_per_sec": 45.6}
{"type": "error", "message": "..."}
```

- `token` events stream as they're generated (mirrors today's per-token loop).
- `done` closes out the turn with the same timing stats the terminal REPL prints today.
- `error` covers inference-server-unreachable and context-overflow (`RESOURCE_EXHAUSTED`) cases — the connection stays open so the client can retry, rather than the server crashing the socket.
- WebSocket disconnect mid-generation cancels the in-flight gRPC `Generate` call, mirroring today's `KeyboardInterrupt` → cancel behavior.

## Components & File Structure

```
Dockerfile                # repl web service image: python:3.11-slim base,
                           # installs requirements.txt (adds fastapi, uvicorn[standard]),
                           # no Metal/CUDA build flags needed (vocab_only is CPU-only)
docker-compose.yml         # single `repl` service
k8s/
  deployment.yaml          # Deployment for the repl service
  service.yaml             # ClusterIP Service, port 8000
  certs-configmap.yaml     # ConfigMap holding the public server.crt (not the private key)
repl.py                    # rewritten: FastAPI app + /ws/chat, no terminal loop
requirements.txt           # + fastapi, uvicorn[standard]
```

`model.py`, `sampling.py`, `context.py`, `config.py`, `inference_server.py`, the `proto/` directory, and `certs/` all stay exactly as the other spec defines them — nothing here modifies them, except that `context.py`'s `truncate_context` and the ChatML formatting move (unchanged) from `repl.py`'s old terminal loop into its new WebSocket handler.

## Docker Compose

```yaml
services:
  repl:
    build: .
    ports:
      - "8000:8000"
    environment:
      - INFERENCE_SERVER_HOST=host.docker.internal
      - INFERENCE_SERVER_PORT=50051
    extra_hosts:
      - "host.docker.internal:host-gateway"   # portable across Docker Desktop and Linux
    volumes:
      - ./models:/app/models:ro
      - ./certs:/app/certs:ro
```

- `extra_hosts` makes `host.docker.internal` resolve on Linux Docker too (Docker Desktop on macOS already provides it automatically; the explicit entry keeps this portable).
- Models and certs are bind-mounted read-only from the host — fast local iteration, no image rebuild needed when the model or certs change.
- `INFERENCE_SERVER_HOST`/`PORT` are read by `repl.py` to build the gRPC channel target, replacing whatever `localhost`-style default the other spec's client code assumes.

## Minikube

```
k8s/deployment.yaml   # 1 replica, image built into minikube's docker daemon
k8s/service.yaml       # ClusterIP, port 8000
k8s/certs-configmap.yaml
```

- **Image build:** `eval $(minikube docker-env) && docker build -t repl:local .` — builds straight into minikube's Docker daemon (docker driver), no registry push needed for local dev.
- **Model file:** baked into the image at build time (`COPY models/ /app/models/`), rather than mounted from the host. Unlike Compose, mounting the Mac host's filesystem into the minikube VM (`minikube mount` / hostPath) is driver-dependent and fragile; baking the file in at build time is the reliable choice for a single-dev-machine cluster. This does mean rebuilding the image when the model changes — acceptable since the model changes far less often than the code.
- **Certs:** the public `server.crt` is mounted via a ConfigMap (it's not secret material — only `server.key`, which stays on the inference server, would need a Secret, and it never leaves the host). `certs-configmap.yaml` is generated from the host's `certs/server.crt` via `kubectl create configmap repl-certs --from-file=certs/server.crt -o yaml --dry-run=client`.
- **Reaching the host's inference server:** `INFERENCE_SERVER_HOST=host.minikube.internal` (available on the docker driver, which is the assumed driver — this project's tooling already targets macOS + Docker Desktop). Set as an env var on the Deployment's container spec, same pattern as Compose.
- **Access from the Mac:** `minikube service repl --url` or `kubectl port-forward svc/repl 8000:8000` — no Ingress controller. This is a local single-user dev setup; adding an Ingress addon buys nothing here.

## Error Handling

- **Inference server unreachable** (not started, wrong port, TLS handshake failure): the gRPC call fails immediately; the WebSocket handler catches it and sends `{"type": "error", "message": "Could not reach inference server at <host>:<port> — is `just serve` running?"}` rather than closing the socket or raising past FastAPI.
- **Context overflow:** server returns `RESOURCE_EXHAUSTED`; relayed as an `error` event, same shape.
- **Client disconnects mid-turn:** the gRPC call is cancelled server-side; no error surfaced (there's no client left to see it).
- Everything else (missing-model traceback, no truncation notice) is inherited unchanged from the other spec — not addressed here.

## Testing

- **WebSocket handler:** tests using Starlette's `TestClient` WebSocket support, with the gRPC client call stubbed out (a fake `Generate` that yields canned `GenerateEvent`s) — verifies the turn orchestration (ChatML formatting, context updates, token relay, error-event shape) independent of the real inference server. The gRPC contract itself is tested in the other spec.
- **Docker Compose:** manual verification — `just serve` running natively, `docker compose up`, connect with a small WebSocket test script (e.g. `websockets` client or `websocat`), confirm a full turn round-trips.
- **Minikube:** manual verification — same round-trip check, against `minikube service repl --url`.

## Setup & Tooling

- **`requirements.txt` additions:** `fastapi`, `uvicorn[standard]`.
- **`justfile` additions:**
  ```
  compose-up:
      docker compose up --build

  minikube-deploy:
      eval $(minikube docker-env) && docker build -t repl:local .
      kubectl apply -f k8s/
  ```
- **`repl` recipe:** repurposed to run the web service locally without Docker (`uvicorn repl:app --reload`), for fast iteration — the old terminal-loop behavior it used to run no longer exists.

## Future (not designed yet)

- Resolving the TLS hostname mismatch (`CN=localhost` cert vs. `host.docker.internal`/`host.minikube.internal`) properly — either by regenerating the cert with those SANs, or overriding the gRPC channel's target name. Deferred; today the containerized client will need one of these to actually establish the TLS connection, but which approach is out of scope for this spec.
- Session persistence / reconnect-and-resume if a WebSocket drops mid-conversation.
- Any real multi-user or production concern (auth, TLS termination at an Ingress, horizontal scaling, resource limits).
